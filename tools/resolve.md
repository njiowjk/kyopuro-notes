# AtCoder Inbox を問題単位で表示する

Vaultのルートで、登録後に必要なタイミングで解決を実行します。

```sh
python3 tools/note.py resolve
python3 tools/note.py list
python3 tools/note.py rebuild
```

通信するのは `resolve` だけです。公開の提出ページから問題リンクを読み取り、同じ問題URLを持つ登録をまとめます。問題URLを直接登録した場合、そのURLからtask IDが確定します。提出は表示上で提出IDの数値順に並び、原本の行順と登録日時は保持されます。代表提出は判定結果を確認できる後続工程まで未選定です。

## 状態と再実行

| 状態 | 意味 |
|---|---|
| `pending` | 未解決。タイムアウト、403、404、429、問題リンクを確認できなかった場合などは、原因が解消したあとに再試行できます |
| `resolved` | 問題IDと問題URLが確定済みで、解法は未整理 |
| `blocked` | 複数の問題リンクやIDの矛盾などを確認。原因の確認まで自動取得・統合を保留 |
| `organized` | 問題ノートと解法を整理済み。Phase 3以降で設定 |

取得は順番に行い、各提出の取得間に1秒待ちます。429を受け取るとその回の取得を打ち切り、先に確認できた結果を保存します。通信エラーで元のURLが失われることはありません。原本の保存後に一覧更新だけが失敗した場合は、`rebuild` で復旧できます。

## JSONLとPhase 3への引き継ぎ

元のレコードは正規化済みの登録URLごとに1行です。バージョン1に状態を追加し、確認した問題URLを `problem_url`、失敗の理由を固定コードの `resolution_error` として必要な行に記録します。以前のバージョン1の行や、Phase 1の3項目形式も読み込めます。

問題単位のデータは原本から組み立てます。同じtask IDに異なる問題URLが確認された場合や、同じ数値の提出IDに異なるURL・問題がある場合は、該当データを統合から外します。問題ノートを作成する処理では、矛盾のないグループだけを使い、既存ファイルを確認してから `問題/AtCoder/{task_id}.md` に反映します。

テストは `python3 -B -m unittest discover -s tools` で実行できます。
