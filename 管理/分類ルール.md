# 分類ルール

## 分野の選択

解法を別の問題で探すとき、成立条件や入力の性質から最初に見る分野を主分類にする。

| 分野 | 選択基準 |
|---|---|
| [文字列](../分野/文字列/文字列.md) | 文字・文字の順序・部分文字列や部分列が中心 |
| [配列](../分野/配列/配列.md) | 添字付きの要素列、区間の集計・更新、並べ替えが中心 |
| [整数](../分野/整数/整数.md) | 数の表現、割り切れ方、剰余、数え上げが中心 |
| [グラフ](../分野/グラフ/グラフ.md) | 一般の頂点と辺の到達可能性・連結性・距離が中心 |
| [木](../分野/木/木.md) | 経路の一意性、親子関係、部分木など木の性質を利用 |
| [グリッド](../分野/グリッド/グリッド.md) | 座標、近傍、盤面の境界、長方形などマス目の性質を利用 |

分野をまたぐ解法は主分類に1ファイルだけ置く。ほかの分野から探す価値があれば、その入口から同じファイルにリンクする。たとえばグリッド固有の境界処理を含む最短移動回数はグリッドに置き、汎用の [BFS](../アルゴリズム/BFS.md) を参照する。

## 解法ノートの追加

- 制約と必要な処理から繰り返し使える型を特定し、既存の分野別ノートとアルゴリズム・典型・STL・数学ノートを確認する。
- 既存ノートで同じ用途を説明できる場合は既存のノートを使う。利用条件、状態の持ち方、境界処理、実装の組み合わせなどに再利用できる違いがあれば、汎用ノートと用途別ノートの重複を許容する。用途別ノートから汎用ノートへリンクする。
- 問題に固有の実装や一度しか使えない工夫は問題ノートに置く。本文の構成は [解法ノート雛形](解法ノート雛形.md) に従う。
- 新規の解法ノートや C++ テンプレートが必要なら、[追加候補](追加候補.md) に保存先・用途・既存ノートとの差・テンプレート案・関連問題を記載する。利用者が保存先と案を承認してから作成する。修正依頼を受けた場合は候補を更新し、保留中は候補のままにする。

## 問題ノートと紐付ける条件

- AtCoderの問題URLの `/tasks/` に続く task ID をファイル名と `task_id` に使い、`問題/AtCoder/<task_id>.md` に問題ごとに1ファイルを置く。既存ファイルがあれば同じIDの新規ファイルを作らない。
- [問題ノート雛形](問題ノート雛形.md) の `problem_url` に問題URLを記録する。自分の提出と確認できたURLを `submission_urls` に重複なく記録し、代表提出を選ぶときはその一覧から `representative_submission_url` に指定する。
- `status` は `unorganized` または `organized` とする。IDと問題URLだけが判明した段階でも `unorganized` で作成できる。解法・実装ポイント・参照元とリンクを確認してから `organized` にする。自作コードと公式解説の要約・出典は対応する節に記載する。
- 提出や解法の説明で実際に使ったと確認でき、解法ノートの適用条件を満たす場合に紐付ける。1問に複数の解法を登録できる。名称の類似だけで紐付けず、作成待ちの解法にはファイルができてからリンクする。

問題ノートのフロントマターは、手動作成でも自動生成でもObsidianの保存形式に揃える。通常の文字列は引用符なしで書き、YAMLで文字列型を保つために必要な場合だけ引用する。未設定の値は `representative_submission_url:` のように値を空欄にし、提出URLが0件なら `submission_urls: []` と書く。以下は整理済みノートの例。

```yaml
---
task_id: abc484_a
problem_url: https://atcoder.jp/contests/abc484/tasks/abc484_a
submission_urls: []
representative_submission_url:
status: organized
---
```

## リンク形式

新規の内部リンクは、リンク元ファイルのディレクトリからの相対 Markdown リンクとする。ファイル名に `.md` を含め、空白を `%20`、パス内の `#` などURLの予約文字を必要に応じてエンコードする。リンク先はリポジトリ内に限定する。既存ノート内の Wikiリンクはそのまま使う。

Obsidianのリンク挿入機能を使う場合は、「Files and links」で `New link format` を `Relative path to file` とし、Markdown形式を選ぶ。[Obsidian のリンク設定](https://obsidian.md/help/settings#links)・[GitHub の相対リンク仕様](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes#relative-links-and-image-paths-in-markdown-files)

以下は将来作成するノート間の記法例。

```markdown
<!-- 問題/AtCoder/abcXXX_d.md の「使用した解法ノート」内 -->
- [1文字違いの判定](../../分野/文字列/1文字違いの判定.md)

<!-- 分野/文字列/1文字違いの判定.md の「関連問題」内 -->
- [abcXXX_d](../../問題/AtCoder/abcXXX_d.md)
```

## 自動管理領域

問題ノートの「使用した解法ノート」は `related-solutions`、解法ノートの「関連問題」は `related-problems` のマーカーで囲む。

```markdown
<!-- BEGIN AUTO: related-problems -->

<!-- END AUTO: related-problems -->
```

- 自動同期は、既存ノートでは対応するマーカーの**内側**のリンク一覧だけを更新できる。開始・終了マーカーは各1行・各1個とし、フロントマター、マーカー行、見出し、説明、コードや手動リンクを含む領域外の内容を元の表記のまま保持する。
- フロントマターの変更判定では、YAMLとして読み取った値を比較する。引用符の有無や `null` と空欄の違いなど、読み取った値が等しい表記変更は差分として扱わず、既存の表記を保持する。
- 例外として、問題ノートの `submission_urls` には、既存項目を保持したまま本人の確認済み提出URLを追記できる。追記がある場合は `submission_urls` の項目だけを編集し、フロントマター全体の再出力は行わない。代表提出と整理状態の変更や、既存本文への解説追記は利用者の編集または明示の指示で行う。
- リンクは1行につき1件とし、相対パスを解決した対象で重複を判定する。パスを比較するときはUnicodeの表記をNFCに揃える。問題側は解法ノートのパス順、解法側は task ID 順に並べる。同じ対応を再処理しても重複を増やさない。
- 更新前に両方のファイル、マーカー、既存リンクを確認する。マーカーの欠落・重複・順序の異常、リンク先の不存在、同時編集による不一致があれば対象を保留する。両方向の変更を一組として扱い、片側だけ更新された状態を残さない。
- 管理領域内の対応は双方で対にする。領域外の手動リンクから自動で対応を追加・削除しない。追加予定のリンクが領域外にすでにある場合は、重複を避けるためその対応の同期を保留する。
