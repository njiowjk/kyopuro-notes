# 承認された解法候補の反映

ユーザーが保存先と C++ テンプレート案を承認した候補を、解法ノートとして Vault に反映する。

> 候補「〈候補名〉」の保存先「〈パス〉」と掲載中の C++ 案を承認します。`.codex/workflows/apply-approved.md` に従って反映し、条件を満たした問題は問題ノートと Inbox の状態も `organized` にしてください。

## 1. 今回の承認範囲を確定する

1. Vault ルートで `git status --short --untracked-files=all` を実行し、作業前の差分を確認する。以下の `python3` は Python 3.11 以降を指し、Windows では利用できる `python` または `py -3` に読み替える。
2. [追加候補](../../管理/追加候補.md) で、ユーザーが今回承認した候補、保存先、案を照合する。候補の記録だけから今回の承認対象を広げない。名前が曖昧、保存先や案が未承認、承認後に案が変わった場合は、該当候補を保留する。候補が残っていれば承認日・保存先・案の要点を記録し、状態を `承認済み` とする。同じ承認記録があれば再利用する。
3. 候補が削除済みなら、[解法ノート一覧](../../管理/解法ノート一覧.md)、実在するノートと関連問題のリンクを照合する。承認した保存先と案および関連問題を確認できるときだけ、残っている工程から再開する。候補やノートの再作成は不要。確認に必要な情報が足りない場合は保留する。
4. 関連問題ノートと原本 `.local/inbox.jsonl` を確認し、task ID と正規化済みURLを照合する。作成の根拠となるソースは [ソース確認手順](analyze-inbox.md#2-ローカルソースと問題を確認する) に従って検証する。コードが実際にその手法を使い、適用条件を満たすことを確かめる。ソースの改版や記録の不一致で承認案との対応が確認できない場合は保留する。この手順では Inbox 全体の再解析や `resolve` は行わない。

## 2. 承認された解法ノートを作成する

- [分類ルール](../../管理/分類ルール.md) と [解法ノート雛形](../../管理/解法ノート雛形.md) に従い、承認された `分野/<分野>/<解法名>.md` に作成する。具体的な用途、成立条件、状態と更新・判定の根拠、計算量、境界条件、主分野と既存ノートへのリンクを記載する。C++17 の例は原則 `main` 中心とし、問題固有の入出力と、自作コードから一般化した点を説明する。
- 承認済みの保存先にノートがあれば、承認案および既存リンクとの整合性を確認して再利用する。解法ノート一覧と既存ノートを確認し、同じ用途の解法ノートが別の場所にある場合や、既存ノートの手書き内容と承認案が一致しない場合は保留する。
- 新規の C++ 例は [共通の検証](analyze-inbox.md#共通の検証) のコマンドでコンパイルし、サンプルと境界条件を確認する。検証できない点や承認案の修正が必要な点があれば、その候補の完了を保留する。

### 双方向リンクを整える

1. 問題ノートの「使用した解法ノート」の `related-solutions` と、解法ノートの「関連問題」の `related-problems` を読む。開始・終了マーカーが各1個で順序が正しく、既存リンク先が実在することを確認する。問題側は解法ノートのパス順、解法側は task ID 順とする。
2. 新規リンクはリンク元からの相対 Markdown リンクとし、拡張子 `.md` を付け、空白は `%20`、パス内の予約文字は必要に応じてエンコードする。相対パスを解決して NFC で揃えた対象で重複を判定する。領域外の手動リンクはそのまま保持し、追加予定のリンクが領域外にある場合は該当の対の同期を保留する。
3. 両方のマーカー内の変更案を先に作り、書き込む前に両ファイルの読取時点からの変更がないことを確認する。対応を一組として更新し、直後に双方を確認する。途中で失敗した場合は、並行編集がない箇所に限って自分の片側の書き込みを元に戻す。安全に戻せない場合は状態更新を止め、確認が必要な箇所を報告する。既存のフロントマター、手書き本文、マーカー行は分類ルールに従って保持する。
4. 現在の CLI には、この双方向リンクを同期するサブコマンドがない。既存ノートの承認待ちの記述などを修正する場合は、ユーザーから本文の編集指示を得て、該当箇所だけを更新する。

## 3. ノートを一覧に登録し、分野入口を同期する

1. ノートの作成、C++ 例の検証、問題ノートとの双方向リンクの整合を確認してから、[解法ノート一覧](../../管理/解法ノート一覧.md) に `- [解法名](../分野/<分野>/<解法名>.md)` の形式で1行を追加する。NFC で揃えた保存先がすでに登録済みなら既存行を使う。
2. `python3 -B tools/note.py sync-domain-links` を実行する。一覧に登録されたリンクを読み、`分野/<分野>/<分野>.md` の `domain-solutions` 内を同期する。対象外の差分が懸念されるときは、書き込みを伴わない `tools/domain_links.py` の `plan_domain_links` で出力予定を確認する。無関係な変更が必要だと分かった場合は同期を保留して報告する。
3. 一覧のリンクが実在するノートを指し、各分野入口から参照できることを確認する。マーカーがない入口の分野名は、同期が成功した場合も出力される。マーカーを新設する場合はユーザーの承認を得る。登録・同期に不備がある場合はその候補を残し、解決後に確認できた工程の続きから再開する。

Phase 3-A の候補を反映した例として、`abc386_c` のリンク、解法ノート、分野入口、一覧の登録を参照できる。[問題ノート](../../問題/AtCoder/abc386_c.md)・[解法ノート](../../分野/文字列/1回以内の文字編集で一致するか判定.md)・[分野入口](../../分野/文字列/文字列.md)・[解法ノート一覧](../../管理/解法ノート一覧.md)

## 4. 登録を確認した候補を削除する

1. [共通の検証](analyze-inbox.md#共通の検証) を行う。分野入口の同期が成功したら同じ入力で `sync-domain-links` を再実行し、`分野入口 0件を更新しました。` と差分で確認する。
2. 候補を削除する前に、関連する問題ノートの管理領域外に、該当候補への案内や承認待ちの記述が残っていないか確認する。本文の編集指示がある場合は、正式な解法リンクを確認してから該当する案内だけを整理する。正式リンクと重複する案内は削除し、ほかの候補への案内や解説、自作コードの記録は保持する。本文の編集指示がなく、旧案内が残る場合は報告する。
3. ノート、双方向リンク、一覧登録、分野入口からの参照を確認した候補だけ、[追加候補](../../管理/追加候補.md) から該当の `##` セクションを削除する。削除前に現行ファイルを読み直し、承認後に変更があれば保留する。ほかの候補と書式を保ち、削除済みのセクションは再作成しない。

## 5. 整理状態を更新し、差分を確認する

1. 今回の承認に関係し、有効な状態が `resolved` の問題だけを状態更新の対象にする。問題ノートの解法・実装ポイント・参照元が確認でき、必要な解法ノート、両方向のリンク、分野入口からの参照が揃い、候補の削除まで完了していて、ほかに保留中の候補や未解決の検証事項がない問題を整理済みにする。[Inbox の状態更新手順](analyze-inbox.md#inbox-の状態更新) に従って問題ノートと原本を更新し、`rebuild` と `list` で確認する。承認待ちや不整合のある問題は保留し、既に `organized` の行と `pending`、`blocked` の行はそのままにする。
2. 同じ承認内容で再実行したとき、ノート、一覧の登録、リンク、状態に追加の変更が不要であることを確認する。
3. `git diff --check`、`git diff`、`git status --short --untracked-files=all` で最終差分を確認する。未追跡の解法ノートも読み返し、変更が承認の範囲に収まり、既存の手書き内容が保たれていることを確認する。

## 報告

反映した候補と保存先、一覧への登録と候補の削除、関連する問題、双方向リンクと分野入口の更新結果、`organized` に進めた問題、保留・未検証事項、コンパイルとテストの結果、再実行時の差分、最終的な Git 差分を報告する。
