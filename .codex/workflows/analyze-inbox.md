# Inbox の解析と解法候補の提案

コンテスト終了後にユーザーが問題URLを `add` で登録し、`resolve` でローカルソースを照合した後に使う。引数なしの `resolve` は `.local/config.toml` の `atc.workspace` を参照する。[CLI の使い方](../../tools/README.md)・[照合手順](../../tools/resolve.md)

> `.codex/workflows/analyze-inbox.md` に従い、開始時点の照合済み問題を整理してください。条件を満たした問題は問題ノートと Inbox の状態も `organized` にしてください。

## 1. 開始時点の対象を確定する

1. Vault ルートで `git status --short --untracked-files=all` を実行し、作業前の差分を確認する。以下のコマンドは Python 3.11 以降で実行する。macOS の例では `python3` を使い、Windows では利用できる `python` または `py -3` に読み替える。
2. 原本 `.local/inbox.jsonl` を `tools/note.py` の `read_inbox` で読み取った時点で、`kind: problem` かつ有効な状態が `resolved` の全行を今回の対象として固定する。照合に使う登録行、正規化済みURL、`contest_id`、`task_id`、`local_source` を控える。task ID の手入力は不要。`python3 -B tools/note.py list` は表示確認に使う。
3. `pending`、`organized`、`blocked`、旧方式の提出行、以後に登録・照合された問題は対象外。`effective_status` が `pending` とするソース記録なしの旧 `resolved` 行と、`conflict_urls` が返す task ID 衝突も対象外とし、理由を報告する。同じURLの行が複数あるなど一意に特定できない問題は保留する。原本の解析に失敗したら書き込まず、CLI が示す行番号と原因を報告する。

## 2. ローカルソースと問題を確認する

1. 原本の正規化済みURLと識別子、`local_source.origin` が `atc-rs-local` であること、および `index`、`language`、`sha256` を確認する。`snapshot_path` が選ぶ `.local/sources/<sha256>.cpp` または `.local/sources/<sha256>.py` の実体を `check_snapshot` で確認する。ディレクトリが Vault 内の通常のディレクトリであることを確認し、スナップショットは生バイトの SHA-256 が完全一致したときに UTF-8 として読む。ファイルが存在しない、読めない、内容が一致しない場合は保留し、今回の作業では再照合や状態の補正を行わない。[Inbox仕様](../../管理/Inbox仕様.md)
2. 登録URLの AtCoder 公式問題文で問題名、入出力、制約、特殊条件とサンプルを確認する。確認できた根拠を記録する。必要に応じて公式解説を読み、自作コードの分析と区別して出典を付ける。必要な情報が得られない場合やコードと題意が合わない場合は、その問題を保留する。
3. コードが保持する状態、初期化・更新・判定、正しさの根拠、計算量、境界条件を整理する。実行できる場合はサンプルと境界ケースで確認し、依存関係や失敗で確認できなかった点を報告する。提出の対応やジャッジ結果は別の根拠で確認できるまで未確認とする。共有ノートにはローカルコードの説明を記し、スナップショット本文や元ファイルのパスは転記しない。

## 3. 既存ノートと照合し、問題ノートを整理する

1. [分類ルール](../../管理/分類ルール.md) に沿って主分野を選び、[解法ノート一覧](../../管理/解法ノート一覧.md) の登録先、`分野/`、`アルゴリズム/`、`典型/`、`STL/`、`数学/` と [追加候補](../../管理/追加候補.md) を検索する。候補を追加する前に、登録済みのノートの本文を読み、名前が違っても用途と適用条件が重なる解法がないか確認する。用途と適用条件が合う既存ノートを再利用し、既存の汎用部品と問題固有の工夫で説明できる場合は問題ノートにまとめる。
2. `問題/AtCoder/<task_id>.md` がなければ [問題ノート雛形](../../管理/問題ノート雛形.md) で作成し、フロントマターと該当する節を埋める。提出が未確認なら `submission_urls: []`、`representative_submission_url:` は空欄にする。整理完了までは `unorganized` とする。同じ task ID のファイルがあれば再利用し、本文と既存の記録を保護する。識別子やURLが異なる場合、または既存本文の更新が必要で指示がない場合は保留する。
3. 実際に使った既存の解法ノートは、対応する管理領域が両側にあれば [双方向リンクの更新手順](apply-approved.md#双方向リンクを整える) に従って結ぶ。汎用ノートなどは、作成する問題ノートの本文で参考として参照できる。必要な管理領域に異常がある場合は同期を保留する。
4. 再利用できる違いがある場合だけ、`管理/追加候補.md` の書式に沿って `提案中` の候補を記載する。候補名、主分野・保存先、用途と適用条件、既存ノートとの差、関連問題、C++17 のテンプレート案、計算量・注意点を記載する。実装例は原則 `main` 内で処理を追える形にする。既存の提案にも同じ用途があれば、必要な関連問題だけを重複なく追記する。承認された案の変更はユーザーに確認する。問題ノートから候補を案内する場合は候補名と追加候補へのリンクを記し、反映完了後は同じ用途を解法ノート一覧から確認できる。解法ノート本体の作成と、そのファイルへのリンクは承認反映時に行う。

Phase 3-A では、`abc399_c` は既存の Union-Find を参照し、`abc386_c` は既存の文字列操作に加えて1回以内の編集判定を候補にした。初回の差分は `git show fd368ce -- 問題/AtCoder/abc399_c.md 問題/AtCoder/abc386_c.md 管理/追加候補.md` で確認できる。[abc399_c](../../問題/AtCoder/abc399_c.md)・[abc386_c](../../問題/AtCoder/abc386_c.md)

## 4. 検証して整理状態を更新する

1. [共通の検証](#共通の検証) を実施する。問題の解法、実装ポイント、参照元が確認でき、必要なリンクが整合し、未反映の解法候補がない問題を整理済みにする。承認待ちや不整合のある問題の状態には手を加えない。原本の対象行に変更がなければ `resolved` のままとする。
2. 整理条件を満たした問題だけ、以下の手順で問題ノートと Inbox を `organized` にする。検証で判明した問題と状態更新の結果を最終差分で確認する。

### Inbox の状態更新

状態更新専用のCLIは現時点で存在しない。両ワークフローの状態更新では、Vault ルートから Python で `tools/` をモジュールの検索パスに加え、`note` の既存の読み書き処理を使う。状態変更は今回の対象行と、新規作成または状態変更を指示された問題ノートの `status` に限る。

1. `file_lock` で `.local/resolve.lock`、`.local/inbox.lock` の順に取得する。その中で `read_inbox` で原本を読み直す。問題行の対象URLと task ID が一意で、元の登録行と `resolved` 状態、ソースのメタデータとハッシュが確認時点と一致することを確かめる。新規行は保持し、競合や途中の変更があれば該当問題を保留する。更新済みの問題は再編集しない。
2. 確認した時点から問題ノートに変更がないことを確かめ、条件を満たすノートの `status` を `organized` にする。既存ノートではユーザーの明示的な状態変更指示がある場合に、その項目だけを編集する。ノートが既に `organized` なら整合性を確認してそのまま使う。続けて、ロック内で読み直したレコード一覧のうち対象行の `status` だけを変え、`write_records(path, inbox, updated)` で保存する。無関係な行のバイト列と順序を保ち、対象がなければ書き込まない。権限や書き込みの失敗時は実際に保存できた範囲を確認し、残った状態差と再開地点を報告する。
3. ロックを解放してから、原本を更新した回に `python3 -B tools/note.py rebuild` を実行し、`python3 -B tools/note.py list` と原本で確認する。一覧から `organized` 行が消えても原本の行は残る。一覧だけの更新が失敗した場合は、原本の保存結果を確認して `rebuild` を再実行する。

### 共通の検証

- `python3 -B -m unittest discover -s tools` で既存テストを実行する。新規の C++17 実装例を検証するときはコードブロックを一時ファイルに取り出し、`g++ -std=c++17 -Wall -Wextra -pedantic example.cpp -o example.exe` または `clang++ -std=c++17 -Wall -Wextra -pedantic example.cpp -o example.exe` を実行する。相当するコンパイラで検証し、可能ならサンプルと適用条件に沿った境界ケースも試す。一時ファイルは Git 管理外に置く。
- 今回追加・変更した相対 Markdown リンクについて、リンク元からパスを解決し、URLエンコードを復号して Vault 内の実在ファイルを指すことを確認する。管理領域内の対は相互に到達でき、NFC で比較したリンク先に重複がなく、規定順で並ぶことを確認する。既存の手動リンクやマーカーの外側は、許可された編集項目を除いて保存前と照合する。
- 同じ対象と入力でもう一度変更を組み立て、同一ファイル、候補、リンク、状態について書き込みが不要と確認する。再実行で対象から消える整理済みの行は原本で確認する。
- `git diff --check`、`git diff`、`git status --short --untracked-files=all` で作業前と比較し、未追跡の新規ファイルも個別に確認する。`.local/` と `Inbox.md` は Git 差分に現れないので、対象行と生成一覧を別途確認する。

## 報告

開始時点の対象件数と task ID、作成・再利用した問題ノート、追加・再利用した候補、`organized` に進めた問題、承認待ち・保留・対象外の理由、検証結果と Git 差分を報告する。ローカルソースの内容と機器固有のパスは報告に含めない。
